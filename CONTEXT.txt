so this app is designed for my personal use only, i upload it to netlify and save the link via safari to my home screen and run it as a PWA.  is it structured well? is there other structure or architecure i should consider adapting or migrating to?


For a personal-use home-screen PWA, the current structure is honestly pretty reasonable. A single-page static app with local persistence, import/export, and a service worker is a good fit for what you’re doing, and it keeps Netlify deployment dead simple. You do not need a backend just to make this app “proper.”

Where it starts to strain is maintainability, not deployability. The main issue is that nearly all behavior lives in one large file, app.js. That makes changes riskier over time because state logic, rendering, persistence, analytics, timers, and import/export are all tightly coupled. For one person using it daily, that’s survivable, but it’s the main structural weakness.

If you want to improve it without overcomplicating it, I’d strongly recommend a gradual modular split while staying vanilla JS:

state.js: app state, migrations, persistence, import/export sanitizing
workout.js: workout generation, set logic, completion flow
history.js: exercise history, analytics helpers, PR/10RM logic
body.js: body metrics and trend calculations
ui/: renderWorkout.js, renderHistory.js, renderAnalytics.js, renderBody.js
pwa.js: service worker registration and update handling
That would give you most of the architectural benefit without forcing a framework migration.

I would only consider a bigger migration if your goals change:

Stay vanilla JS if this is primarily your own tool and you want maximum simplicity.
Move to a lightweight build setup like Vite if you want modules, nicer dev ergonomics, and easier file organization without changing the app model.
Move to React only if you want richer UI composition and are comfortable taking on more tooling and abstraction. For a personal offline-first tracker, React is optional, not necessary.
Move persistence from localStorage to IndexedDB if your session/body/history data will keep growing for years. That’s the first real storage upgrade I’d consider before any framework migration.
My practical recommendation: keep the static PWA architecture, but refactor the codebase into modules before adding more features. That’s the highest-value structural change for this app. If you want, I can do that refactor in-place and keep the behavior the same.

How To Migrate Safely

Do it in stages, not all at once:

Split by responsibility first, while still using localStorage.
Add one central loadState() / saveState() layer so the rest of the app stops touching storage directly.
Swap that storage layer from localStorage to IndexedDB.
Keep JSON export/import exactly as your safety net.
On first launch after the change, read old localStorage, migrate it into IndexedDB, then mark migration complete.
That way the app behavior stays stable while the internals improve.

Why IndexedDB Helps Here

localStorage is okay for small apps, but it’s a brittle place for:

growing session history
body logs over time
rich analytics state
future attachments or more detailed notes
IndexedDB gives you:

much larger storage limits
non-blocking reads/writes
cleaner future growth
better long-term durability for a personal tracker

Findings

P1: Workout typing currently forces full durable-state writes on nearly every keystroke, which will become the main scalability and responsiveness bottleneck as history grows. onSetInput() awaits ApexState.updateWorkoutSet(), which in turn writes both lwo and leh and immediately flushes them in updateWorkoutSet(). The storage layer then serializes and persists the entire cached snapshot in writeCacheToDb() via put(snapshot, STATE_KEY). On an iPhone PWA with a long-lived dataset, this is likely to show up as input lag, dropped frames, and perceived “freezing” during workout logging.
P2: The History tab leaks document-level click handlers every time it re-renders. renderHistory() installs a new document.addEventListener('click', ...) on each render with no guard or teardown. Over time that causes duplicate work, harder-to-reason-about UI behavior, and slow degradation in the exact tab most likely to be opened repeatedly during review/debug sessions.
P2: The facade’s generic update() method is synchronous, but several callers await it as if it provides durable completion semantics. update() only mutates memory, persists localStorage, and schedules the storage mirror; it does not flush IndexedDB. But callers like rerollAll(), toggleLock(), toggleDone() start-time path, and commitBodyMetrics() fallback still await it. That creates a false sense of durability and makes the async facade contract inconsistent across the codebase.
P3: Storage Health can over-report readiness. getStorageStatus() sets initialized from !!storageInitPromise, which becomes true as soon as init starts, not when it succeeds. In practice the UI can say “Ready” while initialization is still pending or after it has fallen back, which weakens the usefulness of the diagnostics you’ve added for this hybrid checkpoint.
Baseline
The good news is the codebase is in a much healthier place than a “broken refactor” state. The shell/runtime split is real, feature ownership is mostly clear, the fallback story is intentional, and the storage facade gives you a workable seam for continued evolution. For a personal offline-first PWA, that is a strong baseline.

The main technical-debt hotspots are:

src/state-facade.js: too many responsibilities in one file
src/features/review.js: analytics/history/session UI mixed together with direct DOM/event lifecycle concerns
src/features/workout-actions.js: performance-sensitive paths still tied to immediate persistence
src/storage/apex-storage.js: whole-app snapshot storage is simple and safe, but it is the long-term scale limiter
Recommended Roadmap

First: decouple workout input from immediate durable flushes. Keep in-memory updates instant, debounce or batch persistence, and reserve flushes for blur, set-complete, add/delete set, and finish-workout.
Second: normalize the facade contract. Either make update() truly async/durable or stop awaiting it and reserve await for explicitly durable helpers.
Third: add one-time listener guards for History/Review tab document events.
Fourth: split state-facade.js by concern after the above stability/perf fixes, not before.
Fifth: if storage work continues later, move from one big app-state blob toward slice-level IndexedDB records only when there’s a clear payoff.
I did this as a static audit and did not run browser or Playwright verification here, so this should be treated as a baseline code review rather than a runtime-certified performance report.
